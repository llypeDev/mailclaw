# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> **Schema or migration change? Update all three dialects (SQLite, PostgreSQL, MySQL).** See "Database schema changes" in AGENTS.md and "Schema and migrations" below.

## Commands

```bash
npm run dev                    # Vite + vinext in local workerd
npm run lint                   # vp lint (Oxlint, lint.config.ts)
npm run build                  # vinext build, including the complete Worker

npm run db:generate            # drizzle-kit generate (SQLite) from src/db/schema/index.ts
npm run db:generate:pg         # same schema, PostgreSQL -> drizzle/migrations-pg
npm run db:generate:mysql      # same schema, MySQL -> drizzle/migrations-mysql
npm run db:smoke -- <DATABASE_URL> [driver]   # exercises migrations + query shapes on any database (MAILCLAW_DB_DIALECT must match)
npm run db:migrate:local       # wrangler d1 migrations apply DB --local
npm run db:migrate:remote      # --remote (needs a concrete database_id in wrangler.jsonc)
npm run db:seed                # POST /api/seed against localhost:3000

npm run deploy                 # vinext build + wrangler deploy; migrate later from Admin settings
npm run preview                # build and preview the vinext Worker locally
npm run cf-typegen             # regenerate cloudflare-env.d.ts from wrangler.jsonc
```

There is no test script in `package.json`; the checks under `tests/` are `node:test` files run with `node --test tests/*.test.mjs` (pass the glob — on Node 24 a bare `tests/` is read as a module path). They must not need Workers bindings, so anything that reaches D1 or R2 belongs in a script under `scripts/` run against `npm run dev` instead.

`next.config.ts` sets `typescript.ignoreBuildErrors: false`, so the Next build (`npm run build:node`) fails on type errors; vinext does not read that option, so `npm run build` (Vite) still does not type-check. `npx tsc --noEmit` is the real check, and the Checks workflow runs it. `tsconfig.json` is `strict` but keeps `noImplicitAny: false`. Lint is at 0 warnings and 0 errors; `no-unused-vars` ignores arguments prefixed with `_` (`argsIgnorePattern: "^_"` in `lint.config.ts`).

`npm run deploy` builds with vinext and uploads with Wrangler. The Cloudflare Vite plugin generates `dist/server/wrangler.json` and redirects Wrangler to it, preserving the custom `worker.ts` entrypoint.

## Architecture

Next.js App Router APIs running on Cloudflare Workers via vinext. Drizzle ORM over D1 by default (or PostgreSQL, MySQL, libSQL via `DATABASE_URL`), R2 for raw MIME, attachments, and record backups, Queues (with dead-letter queues) for async mail processing, a Durable Object for realtime, and two cron triggers for backups and upkeep.

### worker.ts is the entrypoint

`worker.ts` wraps `vinext/server/fetch-handler` and adds handlers Next.js cannot express:

- **`fetch`** — first runs the central CSRF guard (`rejectCrossSiteSessionMutation`, `src/lib/auth/origin.ts`; see Access control), then intercepts `/api/realtime` for the WebSocket upgrade (authenticates the session cookie, then routes to `env.REALTIME.getByName(user.id)`), delegating everything else to vinext.
- **`email`** — the Cloudflare Email Routing handler. Resolves domain routing rules first (`resolveIncomingMail` in `src/lib/email/incoming.ts`) because `message.setReject()` and `message.forward()` only exist here, then applies optional account-level forwarding (loop-guarded by the `MAILCLAW_FORWARDED_HEADER`; the lookup reuses the routing decision), writes raw MIME to R2, and enqueues to `INBOUND_QUEUE`. It never parses mail inline: attachment limits are checked with a linear scan (`inboundAttachmentLimitReasonFromScan`), and the queue consumer re-checks every limit after its one full parse. Order matters for sender retries: a forward rule without a copy runs first (its success decides whether to store); then everything that can throw (forwarding lookup, R2 write, enqueue); forwards that come with a stored copy run last, since `forwardMessage` never throws and a retry after the enqueue would send them twice.
- **`queue`** — a single consumer for all three queues (inbound, outbound, agent); `isInboundQueueMessage`, `isAgentDraftMessage`, `isWebhookRetryMessage` and `isImportJobMessage` in `worker-utils.ts` discriminate the payloads, and the rest are outbound sends. A failure retries with backoff from `msg.attempts` (`queueRetryDelaySeconds` in `src/lib/queues/retry-utils.ts`: 10 s, then ×3 per attempt, capped at 15 min; `retry_delay: 30` only covers an invocation that crashed before calling `retry`); `queueKindOf` picks the retry policy. Inbound and outbound consumers have `max_batch_size: 1`, `max_retries: 5` and dead-letter queues `mailclaw-inbound-dlq` / `mailclaw-outbound-dlq`, which nothing consumes (operators replay by hand); the agent queue has 3 retries and no DLQ. `QUEUE_MAX_RETRIES`/`QUEUE_DEAD_LETTER` must match `wrangler.jsonc` (`tests/queue-retry-policy.test.mjs` checks).
- **`scheduled`** — `0 2 * * *` (backups, account purge then the MySQL-only `runMessageCounterRebuild`, Drive trash, JMAP change pruning, `sweepOrphanedRawMail`, `runDatabaseOptimize`) and `*/5 * * * *` (agent maintenance, follow-up and calendar reminders, `sweepImportJobs`, `sweepStuckOutboundJobs`, and trash retention only on the minute-0 tick via `shouldRunTrashRetention`). `server/runtime/scheduler.ts` mirrors it for Node.

It also re-exports `RealtimeHub`, which must remain exported from the Worker entrypoint. `wrangler.jsonc` sets `placement: smart` (fetch only), `workers_dev: true` and `preview_urls: false` explicitly.

The raw-mail sweeper (`src/lib/email/raw-sweeper.ts`) only deletes unreferenced `inbound/` objects older than 30 days (`RAW_SWEEP_MIN_AGE_MS`), so raw MIME outlives any queue or DLQ copy of its message, and keeps its listing cursor in the bucket at `system/raw-sweeper.json`.

### Mail pipeline

Inbound: `email` handler → R2 → queue → `processInboundMessage` (`src/lib/email/inbound.ts`) → `resolveInboundAddress` routing decision (deliver / reject / forward) → `parseRawMime` (postal-mime) → insert message + attachments → upsert contacts → `dispatchWebhooks` (queued) → `notifyUsersOfNewMessage` over the Durable Object. The consumer groups queries into `db.batch` calls where it can (a batch counts as one D1 query against the Free plan's 50 per invocation; ~18 per message today) and dedupes on `(mailboxId, rawR2Key)`, so a redelivered or replayed message is stored once.

Outbound: `src/lib/email/send.ts` / `sender.ts`, composing with mimetext and sending through the `EMAIL` send_email binding, with `outbound_jobs` rows tracking queued sends. `to`, `cc` and `bcc` accept a header string or an array; `toAddr`/`ccAddr`/`bccAddr` on `messages` store the full comma-joined lists (use `splitEmailAddressList` from `src/lib/email/address.ts`, not `getEmailAddress`, when a value may be a list).

Composer: `src/components/compose/rich-text-editor.tsx` is a contentEditable HTML editor; the body is one HTML string and the text/plain part is derived with `htmlToPlainText` (`rich-text-utils.ts`). Quoted/forwarded content is wrapped by `wrapQuotedHtml` and folded by both the composer and the reader (`splitQuotedHtml`). Forward copies the source's attachments onto the draft (`copyMessageAttachments`); `/api/send` with `draftId` sends them.

Threading: `resolveThreadId` in `src/lib/email/threading.ts` files an inbound or imported message under the thread of the stored message its `In-Reply-To`/`References` name (matched against `providerMessageId` in the same mailbox); otherwise its own Message-ID seeds a new thread. Outbound replies carry `inReplyTo`/`references`/`threadId` from the draft, and a fresh send is keyed by the Message-ID Cloudflare returns. `/api/messages/[id]/thread` returns the conversation. Lists pass `group=thread` (the "conversation view" toggle, `use-conversation-view.ts`) to get one row per thread plus `threadMessageIds`, which row actions and bulk actions expand to.

### Sending and receiving providers are per domain

`domains.sending_provider` (`none | cloudflare | resend | ses`) and `domains.receiving_provider` (`none | cloudflare | resend | ses`, default `cloudflare`) are chosen independently on the Domains page; DNS stays on Cloudflare either way. They record intent: switching a provider never touches DNS, each provider's own Setup does, and a **Clean up** button removes the config of an unselected provider.

- **Sending** goes through `sendThroughProvider` (`src/lib/email/outbound-provider.ts`), which `deliverEmail` and `sendSystemEmail` call after `getOutboundProviderConfig(env, from)` resolves the provider from the From domain (`none` throws). Cloudflare keeps its 5 MiB link fallback; Resend and SES take attachments directly. Resend and SES return different Message-IDs than we send, so `providerMessageId` stores the one replies will carry (`<id@email.amazonses.com>` or `<id@region.amazonses.com>` for SES).
- **Receiving** from a non-Cloudflare provider enters through `intakeProviderMail` (`src/lib/email/provider-intake.ts`) and then the same `intakeIncomingMail` as everything else, once per recipient on a known domain. Providers cannot be rejected to after accepting, so reject and size limits drop the message, and `forward` is unavailable. Inbound endpoints are public and authenticate themselves: `/api/inbound/resend` verifies the Svix signature (`svix.ts`) with the secret Resend returned when `ensureWebhook` created the hook (`app_settings.resend_webhook_secret`), then fetches the raw MIME from `raw.download_url`; `/api/inbound/ses` is an SNS HTTPS endpoint guarded by a secret token in its URL, the topic ARN and reading the object from our own bucket.
- **Only one MX owner per domain.** `publishMx` (`receiving-dns.ts`) refuses with `MxConflictError` (HTTP 409 `MX_CONFLICT`) when other MX records exist; the UI confirms and retries with `replaceMx`. Cloudflare Worker routes (`ensureMailboxDomainRouting`) are created only for domains whose receiving provider is `cloudflare`.
- **Resend** keeps one key (`app_settings.resend_api_key`, or `RESEND_API_KEY`) and one Resend domain per hostname carrying both capabilities, so sending cleanup disables only `sending` when the domain still receives through Resend and vice versa. Apex MX values matching `inbound-smtp.*.amazonaws.com` are receiving records; everything else is sending.
- **AWS** (`src/lib/aws/`) is a hand-rolled SigV4 client (`sigv4.ts`, verified against AWS's published vectors in `tests/provider-aws-resend.test.mjs`) so it runs on Workers and Node without the SDK. Credentials live in `app_settings.aws_config` (or `AWS_*` env vars) and are validated before saving by `validateAwsConfig`, which proves identity with STS then probes SES, SNS and S3, reporting each missing permission with the IAM policy that grants it. SES sending uses SESv2 (`ses.ts`); receipt rules exist only in SES v1 (Query protocol), so receiving uses `awsQuery`. `setupSesReceiving` creates the S3 bucket and policy, SNS topic, policy and HTTPS subscription, then a per-domain receipt rule in the account's active rule set (creating `mailclaw-inbound` only when none is active), and the MX. State is in `app_settings.ses_receiving`. SES inbound exists only in some regions (`SES_RECEIVING_REGIONS`) and needs a public HTTPS `APP_URL`.

### Routing rules have two scopes

`routing_rules.scope` splits two genuinely different mechanisms, and mixing them up is the easy mistake:

- **`domain`** — evaluated by `resolveInboundAddress` (`src/lib/email/routing.ts`) *while resolving the address*, in three phases: `reject` rules first (so a sender can be blocked even when the recipient is a real mailbox), then exact mailbox and alias lookup, then `forward`/`store` catch-all fallbacks. Ordered by descending `priority`, then oldest first. This phase split is what stops a `*` catch-all from shadowing real mailboxes — preserve it.
- **`mailbox`** — evaluated by `resolveInboxRuleDestination` *after* delivery, to pick a folder or move to spam/trash.

Both queries filter on `scope`, so any new rule must set it explicitly. `forward` and `reject` are actioned in `worker.ts`, never in the queue consumer.

### Webhook deliveries ride the outbound queue

`dispatchWebhooks` (`src/lib/email/webhooks.ts`) inserts a pending `webhook_deliveries` row per subscribed hook and enqueues every attempt onto `OUTBOUND_QUEUE`, the first one included (no delay), so a slow endpoint never holds up the inbound or send path; if the enqueue throws it falls back to delivering inline. The message kind is still `webhook.retry` for history. Each attempt records status, error snippet, duration and `nextRetryAt`; failures re-enqueue with a `delaySeconds` backoff rather than adding a third queue binding. `env.d.ts` widens `OUTBOUND_QUEUE` to the union of both payload types accordingly. `runDelivery` is shared by the queue and the manual retry endpoint; the queue path passes `skipSettled`, so an at-least-once redelivery never posts a `delivered` or `exhausted` delivery again (only the manual retry does).

### Cloudflare is a live dependency, not just a host

Domain and mailbox management call the Cloudflare API at runtime (`src/lib/cloudflare-api.ts`, `src/lib/domains/`). Adding a domain enables Email Routing DNS and sending subdomains on the zone; creating a mailbox creates a Cloudflare Email Routing rule targeting the Worker named by `getEmailWorkerName()` (`src/lib/cloudflare-api-utils.ts`); removing a domain cleans those up (`src/lib/domains/cloudflare-cleanup.ts`).

Consequence: `getEmailWorkerName()` returns the hard-coded `"mailclaw"`, so the deployed Worker `name` and `services[].service` for `WORKER_SELF_REFERENCE` in `wrangler.jsonc` must both be `mailclaw`. Cloudflare service bindings need a literal name and cannot reference the top-level `name`. `CF_EMAIL_WORKER_NAME` is still described in `package.json` (`cloudflare.bindings`), but no code reads it.

If Cloudflare refuses Email Sending while a domain is provisioned with routing (401/2036, usually Workers Free, or 403; `isSendingAuthorizationError` in `sending-subdomain.ts`), `provisionDomainOnCloudflare` (`src/lib/domains/provision.ts`) keeps the domain receive-only (`sendingProvider: "none"`) and returns `sendingUnavailable` instead of failing; the register page shows `setup.sendingUnavailable`.

Outbound calls to services we do not run go through `withTimeout` (`src/lib/http/fetch-timeout.ts`: API 30 s, send 60 s, raw transfer 120 s, push 10 s). Bodies from outside are read with `readBodyWithLimit` (`src/lib/http/limited-body.ts`).

Auth is `CF_TOKEN` (preferred) or the legacy `CF_EMAIL` + `CF_API_KEY` pair.

### The database is D1 unless `DATABASE_URL` says otherwise

`docs/databases.md` is the user-facing reference; this is how it works.

- **Selection.** `resolveDatabaseConfig` (`src/db/dialect.ts`, pure) maps `DATABASE_URL` (+ `DATABASE_DRIVER`, `DATABASE_AUTH_TOKEN`, or a `HYPERDRIVE` binding) to a dialect (`sqlite | postgres | mysql`) and driver. No URL means D1 on Workers or the better-sqlite3 file when self-hosted, exactly as before. `withDatabase(env)` (`src/db/with-database.ts`, applied next to `withStorage` in `getEnv()`, each `worker.ts` handler and the Node env) replaces `env.DB` with an `ExternalDatabase`; every caller still reads `env.DB`.
- **One schema, three dialects.** `src/db/schema/index.ts` is written against a kit (`schema/kits.ts`): `table`, `text`, `integer`, `bool`, `timestamp`, `autoId`, `index`, `uniqueIndex`, `desc`, `nowSeconds`. `schemaDialect()` picks the real builders when the module is first imported (from `process.env`, which Workers populate from vars; `MAILCLAW_DB_DIALECT` forces it for tooling), so only one dialect's tables exist per process. The exported tables are *typed* as SQLite whichever dialect is active; that is deliberate, because the app only uses query-builder calls all three share. Representation is kept identical across dialects so raw SQL stays portable: timestamps are seconds in a `bigint`, integers are `bigint`, booleans are native. MySQL needs VARCHAR for anything indexed, so `text()` there returns a recorder resolved in `table()` once the index callback shows which columns are keys; wide indexes are trimmed to InnoDB's 3072 bytes, expression key parts and `uniqueIndex().where()` degrade (see docs).
- **Drivers are executors.** `src/db/drivers/*` turn `(sql, params)` into rows, lazily importing the package (`pg`, `postgres`, `@neondatabase/serverless`, `@electric-sql/pglite` (Node only), `mysql2`, `@planetscale/database`, `@libsql/client`, better-sqlite3, bun:sqlite). `external.ts` feeds an executor to drizzle's `pg-proxy` / `mysql-proxy` / `sqlite-proxy` and to `CompatDatabase` (`d1-compat.ts`), the D1-shaped `prepare().bind().run/first/all`, `batch`, which keeps the ~25 raw `env.DB.prepare` call sites working (`?` becomes `$n` for PostgreSQL). Workers cannot reuse sockets across requests, so TCP drivers connect per query unless `shared` (Node).
- **`getDb` caches per D1 binding.** `createDb` keeps one drizzle instance per D1 binding object in a `WeakMap` (building one walks the whole schema, and `getDb` runs hundreds of times per request path); a D1 session from `withSession` is a different object and gets its own. External databases are never cached: their instance holds an open batch's connection on `ctx.tx` (`compat.ts`), and one `ExternalDatabase` serves the whole process, so sharing it would let a concurrent request run inside another's transaction.
- **`compat.ts` keeps the SQLite-shaped API.** It adds `db.run/all/get/values/batch` to PostgreSQL/MySQL instances, and on MySQL shims `insert().onConflictDoNothing/DoUpdate().returning()`, `update().returning()`, `delete().returning()` (ON DUPLICATE KEY UPDATE plus a select by primary key; claims rely on the affected-row count, so mysql2 keeps `FOUND_ROWS` semantics).
- **Dialect-specific SQL lives in `src/db/sql.ts`** (`insensitiveLike`, `excluded`, `greatest`, `charIndex`, `concatText`, `matchNothing`, `escapeLike`) and `src/db/introspect.ts` (`listTableNames`, `listColumnNames`, `quoteIdentifier`). New raw SQL must work on all three: no bare `0`/`1` as a boolean (`WHERE 1 = 0`), no `x = 0` on boolean columns (`NOT x` / `case when x`), no `||` for strings on MySQL, quote reserved words (`key`, `read`, `repeat`, `change`) via `sql.identifier` or drizzle columns, no `ON CONFLICT ... DO UPDATE SET col = col + 1` in raw SQL (use `onConflictDoUpdate` with `sql\`${table.col} + 1\``). Error text matching goes through `src/lib/database-errors.ts`, which knows all three vocabularies.
- **Search.** SQLite keeps the FTS5 index below; PostgreSQL and MySQL have no index and `buildSearchConditions` falls back to case-insensitive substring `LIKE` predicates (pg_trgm GIN indexes are added to PostgreSQL when the extension is allowed).

### Schema and migrations

Schema lives in one file: `src/db/schema/index.ts` (about 60 tables). Each dialect has its own migration directory and bundle: `drizzle/migrations/` (SQLite, full history, ledger `d1_migrations`), `drizzle/migrations-pg/` and `drizzle/migrations-mysql/` (a generated `0000_baseline` plus the hand-written `0001_triggers_and_seeds`, ledger `mailclaw_migrations`). **A schema change needs a migration in all three**, plus its trigger/seed twin when it touches `messages`, `folders`, `mailboxes` or `mailbox_aliases`; `tests/database-dialects.test.mjs` fails when the dialects diverge or a bundle is stale. Note that `drizzle-kit generate` currently prompts interactively about a snapshot rename conflict for SQLite, so recent SQLite migrations were hand-written to match the generated style. SQLite `0088` and `0089` are deliberately absent from `drizzle/migrations/meta/_journal.json` (as `0041`–`0051` are); the PostgreSQL and MySQL twins (`0012`, `0013`) are in their journals. No runner reads the SQLite journal: the bundle generator, Wrangler and the Node runner all go by filename order, so a journaled newer file can never run before an older unlisted one. The SQLite snapshots in `meta/` are older still (latest `0080`), so review what `db:generate` emits.

`npm run db:bundle` packages the SQL files for the Worker (`src/lib/migrations/bundle.json`, `bundle-postgres.json`, `bundle-mysql.json`). `/api/setup/prepare`, the admin migration endpoint and (self-hosted, non-SQLite) server start use the shared runner in `src/lib/migrations/service.ts`. PostgreSQL and MySQL bundles split only on `--> statement-breakpoint`, because function and trigger bodies contain semicolons. Build, deploy, preview, and development scripts generate the bundle before loading application code.

Concurrent runs are safe per dialect. SQLite/D1: each migration plus its ledger insert is one atomic batch; a loser's insert fails, it rolls back and re-reads the ledger. PostgreSQL: every migration transaction (and the ledger creation) starts with `pg_advisory_xact_lock(POSTGRES_MIGRATION_LOCK_KEY)`, transaction-scoped because Workers drivers open a connection per query. MySQL commits DDL implicitly, so `withMysqlMigrationLock` takes `GET_LOCK('mailclaw_migrations', 120)` on the one connection the executor's `transaction` hook pins (commits that transaction at once, then runs everything on it), and `applyMysqlMigrations` records progress after each statement as a ledger row `<name>#partial:<n>`, renamed to `<name>` after the last statement; a failed run resumes at statement `n`, tolerating an "already exists"-style error on that first statement only (`isAlreadyAppliedMysqlError`, `service-utils.ts`). `getAppliedMigrationNames` filters `#partial` rows, so the migration stays pending. Drivers without a `transaction` hook, or a refused `GET_LOCK`, run unlocked with a warning. After any migration applies, the runner calls `optimizeSqliteDatabase` (`PRAGMA optimize`, SQLite dialect only; `src/lib/migrations/optimize.ts`), which the daily cron and Node start repeat.

The setup path only ever initializes an empty database — it refuses to touch one that already has tables.

### Object storage is `env.BUCKET`, from R2, Backblaze B2 or AWS S3

Every blob (raw MIME, attachments, Drive, avatars, branding icon, JMAP uploads, backups) goes through `env.BUCKET` with the R2 API. `withStorage` (`src/lib/storage/index.ts`) swaps `BUCKET` for `B2Bucket` (`b2-bucket.ts`, S3 API signed with the shared SigV4 client; it serves AWS S3 too) when `getObjectStorageConfig` finds all of `B2_*` (Backblaze, wins) or `S3_BUCKET`/`S3_REGION`/credentials (AWS S3, credentials falling back to `AWS_*`); otherwise the R2 binding (or the Node file bucket) is untouched. It is applied in `getEnv()`, at the top of each `worker.ts` handler (which receive the raw env) and in the Node runtime env. `B2Bucket` implements only what the app calls (`get` with range, `head`, `put`, `delete`, multipart); if new code needs another R2 method, add it there. Do not read `cloudflare:workers` env directly for storage. `GET/POST /api/v1/storage` and the `manage_storage` MCP tool (admin scope `storage`) report and test it.

### Two runtimes, one code path

The Node build aliases `cloudflare:workers` to `server/runtime/cloudflare-workers.ts`, allowing the shared helper to use its existing `getNodeEnv()` fallback. That alias only applies when `MAILCLAW_RUNTIME=node`; vinext uses the native Workers module. Next outputs to `.next-node` so its generated types do not collide with vinext's `.next/types`.

The app reaches every platform service through `getEnv()` (`src/lib/cloudflare.ts`). On Workers that is the native `cloudflare:workers` env. In the self-hosted runtime, `server/index.ts` builds an object with the same shape (`server/runtime/env.ts`: a D1-compatible wrapper over better-sqlite3, an R2-compatible file bucket, `EMAIL` over nodemailer or the Cloudflare Sending REST API, in-process queues, a WebSocket hub standing in for the Durable Object, a fixed-window rate limiter) and publishes it as `globalThis.__mailclawNodeEnv` before Next starts; `getNodeEnv()` in `src/lib/runtime.ts` returns it. Application code must not care which one it got. The few places that must differ check `isNodeRuntime(env)`: setup requirement checks, the self-update button, and domain provisioning, which without Cloudflare credentials records the zone as `"manual"` (`src/lib/domains/provision.ts`) so every Cloudflare call is a no-op and the DNS page lists records to set by hand. Inbound mail off Workers goes through `intakeIncomingMail` (`src/lib/email/intake.ts`) from either the SMTP listener (`server/runtime/smtp.ts`) or the signed `/api/inbound` webhook the relay Worker in `deploy/cloudflare-email-relay` calls. `npm run build:node` builds Next in Node mode and bundles the server with esbuild to `dist/server.mjs`; the Dockerfile runs that. Migrations are applied from `drizzle/migrations` at start (`server/runtime/migrate.ts`), in filename order like the bundle runner (not journal order), skipping names already in `d1_migrations`, so the bootstrap schema in `src/lib/setup/migration.ts` is not used there.

Node-only behaviour to keep in mind:

- **SMTP** (`server/runtime/smtp.ts`, pure parts in `smtp-utils.ts`) decides each recipient at `RCPT TO` (`checkRecipient`): 550 for an unmanaged domain, an address that resolves to nothing, or a domain `reject` rule; 451 if the lookup throws. After DATA one reply covers all recipients (`smtpDataReply`: any failure 451, all refused 550, else 250). `CompletedWork` remembers, per `messageFingerprint` (envelope sender + bytes), recipients finished and forwards sent, in memory for 24 h, so a sender's retry after a 451 does not repeat them. Forwards sent by `intakeIncomingMail` carry the `X-Mailclaw-Forwarded` marker too.
- **Queues** are `InProcessQueue` (`queue.ts`): per-queue concurrency (inbound 2, outbound 4, agent 2), `QUEUE_MAX_RETRIES` and `queueRetryDelaySeconds` from the Workers policy, no DLQ (exhausted jobs are logged and dropped). Jobs are in memory, so on start `server/index.ts` runs `requeueScheduledOutboundJobs` and `requeueUnprocessedInbound` (`inbound-recovery.ts`: `inbound/` objects under 24 h old that no message references, bounded to 1,000, headers re-read from the object and verdicts/sender IP from its `customMetadata`, written by intake) before the listeners start.
- **Env** is an allowlist: `PASSTHROUGH_VARIABLES` in `server/runtime/env.ts` (checked against `env.d.ts` by a test). A new setting read through `env` must be added there, or Node silently ignores it.
- **CSRF**: `rejectCrossSiteNodeRequest` (`http-guard.ts`) applies the same `rejectCrossSiteSessionMutation` before Next, rebuilding the browser's origin from `X-Forwarded-Proto`/`X-Forwarded-Host` only with `TRUST_PROXY`, else from the socket and `Host`.

### JMAP lives in `src/lib/jmap/`

`handleJmapRequest` (`src/lib/jmap/handler.ts`) owns `/jmap/*` and `/.well-known/jmap`; the Next routes under `src/app/jmap/[[...segments]]` and `src/app/.well-known/jmap` only delegate to it, and it is framework-free so it could be mounted from `worker.ts` too. Auth is an API key with the `jmap` scope via `authenticateApiRequest` (`src/lib/api/key-auth.ts`, the Next-free core that `src/lib/api/auth.ts` now wraps). JMAP Mailbox ids encode `mailboxId`, `mailboxId~role` or `mailboxId~f~folderId` (`ids.ts`); `email-query.ts` maps filters onto `messages` columns, `email-objects.ts` builds Email objects from stored rows (no MIME parsing).

`processRequest` memoizes the accessible mailboxes and the change scope on `ctx.memo` across read-only calls of one request; write methods run with `memo: null` because they read `oldState` and `newState` in the same call.

States are positions in a change log (`changes.ts`): the `jmap_changes_*` triggers of migration 0065 (PostgreSQL and MySQL: `0001_triggers_and_seeds`) write a row per created, updated or destroyed message and per folder or mailbox change into `jmap_changes`, so `Email/changes`, `Mailbox/changes` and `Thread/changes` return real deltas (`Email/queryChanges` still answers `cannotCalculateChanges`). A state is `c1:<seq>:<access fingerprint>`; a sharing change alters the fingerprint, and the daily cron prunes rows older than 30 days and raises `jmap_change_floor`, and either makes older states answer `cannotCalculateChanges`. Like `jmap_mailbox_revisions`, these tables are derived and excluded from backups. Never write to them from application code.

### Mobile apps: device keys and native push

`POST /api/auth/device` signs a mobile app in with email + password (+ MFA via the login challenge) and returns a `jmap`-scoped API key of `kind = 'device'`, named after the device. It has its own rate limit (`DEVICE_LOGIN_RATE_LIMIT`) since it skips Turnstile. Device keys are listed and revoked under Settings → Security (`/api/devices`), hidden from the API keys list, and `deleteUserSessions` revokes them all (password change, reset, MFA change). Apps register their APNs token with `PUT /api/mobile/push` using the device key; `push_devices` rows cascade with the key. `notifyUsersOfNewMessage` fans out to `sendNativePush` (`src/lib/push/native.ts`), which needs the `APNS_KEY_ID`, `APNS_TEAM_ID` and `APNS_PRIVATE_KEY` secrets and encrypts sender and subject to each device's P-256 key (`native-crypto.ts`), or sends a content-free alert when the device turned previews off.

Native push goes straight to APNs when the server has `APNS_KEY_ID`/`APNS_TEAM_ID`/`APNS_PRIVATE_KEY`, or through a push relay (`mailclaw-relay`, set `APNS_RELAY_URL`) when it has none. The app decides per registration: it trades its APNs token for a relay handle (`mfr1.…`, `src/lib/push/relay.ts`) and registers that as `token`; `sendNativePush` routes handles to the relay and hex tokens to Apple. `push_devices` is unique per (platform, token, user), and a device key keeps one registration (`registerPushDevice` deletes the one it replaces). The PUT response's `deliverable` says whether this server can send for that token, so the app can fall back from a handle to the raw token.

`Email/set` create and `Email/import` share one insert (`insertDraft` in `emails.ts`) and one target rule (`resolveDraftsMailbox` in `email-import-utils.ts`): a new message goes into exactly one Drafts mailbox, never Inbox or a folder, because delivered mail is the inbound pipeline's job. `Email/import` parses the uploaded blob with `parseRawMime`, stores the `Message-ID` in `providerMessageId` with its angle brackets (as inbound rows do) and keeps the uploaded bytes at `drafts/<messageId>.eml` in `rawR2Key`, so `readBlob` serves the client's own MIME back instead of the rebuilt minimal message; the `jmap-uploads/` object is deleted once claimed. `Email/copy` and `Email/parse` are still `emailUnsupported`.

`email-query.ts` answers the `header` filter from columns — `Message-ID` from `providerMessageId` (compared with and without angle brackets, since inbound rows store them and outbound rows do not), `In-Reply-To` from `inReplyTo`, `References` by a padded `LIKE` on the space-joined chain. Any other header name throws `unsupportedFilter` (RFC 8620 §5.5). Filter conditions must never be silently dropped: a client that de-duplicates with `header` would otherwise match every message in the mailbox.

### Password reset and MFA

`reset_email` on `users` is the destination for reset links (`src/lib/auth/password-reset.ts`); links are hashed, single-use, 30 minutes, and redeeming one revokes every session. Reset mail is sent by `sendSystemEmail` (`src/lib/email/system-mail.ts`), which writes straight to the send binding from the first admin mailbox on a sending-enabled domain, so nothing lands in Sent and no webhooks fire. If no domain can send, the request still returns 200 and a warning is logged. TOTP lives in `src/lib/auth/totp.ts` (RFC 6238 over Web Crypto, no dependency); the secret is stored on `users` at enrolment but only counts once `totp_enabled` is set by a verified code. A login with MFA returns `{ mfaRequired, challengeToken }` (`login_challenges`, 5 minutes) instead of a session, and `/api/auth/mfa/verify` finishes it with a TOTP or recovery code. Each second-factor try goes through `getLoginChallengeUserId`, a conditional `UPDATE … SET attempts = attempts + 1 WHERE attempts < 5 RETURNING`, so a challenge allows `MAX_LOGIN_CHALLENGE_ATTEMPTS` (5) tries and concurrent requests cannot share the last one; steps that check no factor (starting a passkey ceremony) use `peekLoginChallengeUserId`. Before migration 0088 the column is missing and tries are not counted. Password changes and admin resets call `deleteUserSessions`.

Passwords are scrypt in PHC form, `$scrypt$ln=14,r=8,p=1$<salt>$<hash>` (`password-utils.ts`; N = 2^14 is the most workerd accepts with r = 8, ~40–60 ms CPU). bcrypt rows still verify and `upgradePasswordHashIfNeeded` (`password-upgrade.ts`) rehashes them after a successful `/api/auth/login` or `/api/auth/device`, with an update conditional on the old hash so it cannot undo a racing password change. `parseScryptHash` rejects out-of-range parameters rather than trusting the row.

### Read receipts are an opt-in pixel

The composer's eye toggle (`use-track-opens.ts`) starts from the account default in `user_compose_preferences` (Settings → Inbox → Compose, `/api/settings/compose`, migration 0072, off before it) and sends `trackOpens`; toggling it changes only that message. The same table holds `undo_send_seconds` (migration 0073, 0/5/10/15/30, default 15), which `sendEmail` reads for `undoSend` requests; 0 delivers at once. `deliverEmail` creates the `message_tracking` token at actual delivery, so a cancelled undo-send or reschedule leaves none, and injects the pixel only into the HTML handed to the provider: the stored Sent copy never contains it. The pixel is `GET /api/i/<token>.gif` (public, always the same GIF); `classifyOpen` (`src/lib/tracking/open-tracking-utils.ts`) names the client and device, drops device and location for proxies (Gmail, Yahoo, Apple), and flags Apple Mail Privacy Protection (Apple ASNs) and fetches within 10 s of delivery as `automated`, which `open_count` excludes. Pixel origin is the sender domain's own host from `domain_tracking_hosts` (set on the Domains page, must be the domain or a subdomain and attached to the Worker as a custom domain, kept out of `domains` so sending never depends on migration 0069), else `APP_URL`, else the composer request's origin; with neither, or before migration 0068, mail goes out untracked rather than failing. One pixel per message, so opens are not attributed to a recipient.

### Spam scoring adds up signals

`analyzeSpam` (`src/lib/spam/engine.ts`) sums scored signals from the analyzers in `src/lib/spam/analyzers/`, contact relationships, per-mailbox reputation and the Bayesian classifier, then applies `SPAM_THRESHOLDS` (`weights.ts`). Authentication is trusted only from the receiving side: verdicts SES computed (the SNS receipt for SES intake, the leading `X-SES-*`/`Authentication-Results: amazonses.com` block for Resend intake, read by `readSesTrace`) ride the queue message as `verdicts`, and otherwise only a Cloudflare-written `Authentication-Results` header counts. `ExternalSpamIntelligenceProvider` adds Spamhaus DQS (ZEN, DBL), abuse.ch URLhaus and RDAP domain age; each lookup is optional, time-limited, cached in memory and under `spam-cache/` in `env.BUCKET` (the Cache API does nothing on workers.dev), and a failure adds no signal. Spamhaus' public mirrors refuse queries from public resolvers such as our DoH endpoint, so only DQS keys work. Keys, the domain-age switch and installation-specific brands live in `app_settings` (admin Spam filter page, `src/lib/spam/settings.ts`), falling back to the `SPAMHAUS_DQS_KEY`, `ABUSECH_AUTH_KEY` and `SPAM_DOMAIN_AGE_CHECK` env vars; reading them tolerates a database without migration 0070. Keep regional brands out of the built-in list in `impersonation.ts`.

### Follow-up reminders surface unanswered sends

The composer's bell (`FollowUpMenu`) sends `followUpDays`; `deliverEmail` arms a `follow_ups` row once the message is actually out, so cancelled undo-sends leave none. The five-minute cron (`runFollowUpReminders` in `src/lib/follow-ups/service.ts`, also in the Node scheduler) moves due rows to `due`, or to `replied` when an inbound message joined the same thread in the same mailbox after the send; listing and reading re-check that, so a late reply closes a reminder too. Due reminders are not inbox rows: `DueFollowUps` pins them above the first inbox page, linking to the Sent message, with snooze and done. Reminders belong to the user who armed them. Before migration 0071 every reader returns nothing and arming is skipped.

Optional tables are detected with `isMissingTableError` (`src/lib/database-errors.ts`): drizzle rethrows driver errors as "Failed query" with the SQLite message on `cause`, so matching `String(error)` misses it.

### Calendar reminders are Web Push from the five-minute cron

`calendar_events.reminder_minutes` (null = none, 0-10080) is set in the event editor. `runCalendarReminders` (`src/lib/calendar/reminders.ts`, in `worker.ts` `scheduled()` and the Node scheduler) reads candidates in two keyset-paged queries on `calendar_events_reminder_idx` (`repeat`, `starts_at`; migration 0088): one-off events due within the 7-day maximum offset and not yet reminded, and series still running, both only for users with Calendar enabled. It expands each candidate with `expandToolEvents` and pushes every occurrence whose start minus the offset has passed and that has not started. `last_reminded_start` is claimed with a conditional update before sending, so overlapping runs never notify twice; editing an event resets it. Delivery is `sendPushContent` (`src/lib/push/server.ts`), the generic form that `sendPushNotifications` now wraps; native APNs push is not wired to reminders. Before migration 0078 the cron does nothing (`isMissingColumnError`).

### Imports are background jobs

`/api/import/messages` (uploads) and `/api/import/imap` only validate and create a row in `import_jobs`, then answer 202 with the job; nothing is imported inside the request. `processImportJob` (`src/lib/import/jobs.ts`) handles one chunk per `import.run` message on `OUTBOUND_QUEUE` (like webhook retries, so no extra binding), records counters and the resume `cursor` on the row, and enqueues the next chunk itself. Uploaded files are split and staged in the bucket as `import-jobs/<id>/<n>.bin` batches (`staging.ts`), deleted as consumed. IMAP jobs read the folder list from `spec`, but the password never touches the database: it rides along in each queue message, so a lost message fails the job instead of resuming. Cancelling flips the status; every chunk's final write is conditional on the job still being active. `sweepImportJobs` (cron / Node scheduler) fails jobs idle for 30 minutes and prunes finished records after 7 days. The import page polls `GET /api/import/jobs`; `DELETE /api/import/jobs/[id]` cancels an active job or dismisses a finished one. IMAP chunks pipeline their FETCHes (sizes first via `RFC822.SIZE`, then groups bounded by `planImapFetchGroups`). Chunk size is adaptive: `cursor.size` halves when a chunk throws (retried up to 4 times, except credential errors) or when the queue redelivers the message (`attempt` from `msg.attempts`, e.g. a resource-limit 503), and climbs back after clean chunks. A failed job can be resumed (`resumeImportJob`, `POST /api/import/jobs/[id]/resume`): it re-queues from the saved cursor, IMAP asks for the password again, and file jobs keep their staged batches until dismissed or pruned. An IMAP source the server cannot open (`isMissingImapFolderError`, e.g. Gmail's `[Gmail]` parent) is skipped with a recorded error instead of failing the job. `import_jobs` is in `INTERNAL_TABLES`, so backups skip it.

### Search is an FTS5 index kept by triggers

`messages_fts` (migration 0030) is an external-content FTS5 table over `messages` (SQLite only; other dialects use the `LIKE` fallback in `conditions.ts`); three triggers in the same migration keep it in sync on insert, update and delete, so no application code touches the index. `buildSearchConditions` in `src/lib/search/conditions.ts` turns the Gmail-style grammar (`src/lib/search/query-utils.ts`) into a `rowid IN (SELECT rowid FROM messages_fts WHERE messages_fts MATCH ?)` predicate plus plain column filters; a query made only of negations becomes `rowid NOT IN (… MATCH ?)`, since FTS5 cannot match "everything except". The `LIKE` fallback wraps columns in `coalesce(col, '')` so a negated term keeps rows whose column is NULL. Two consequences: the bootstrap SQL in `src/lib/setup/migration.ts` is split with `splitSqlStatements`, which keeps trigger bodies whole; and the backup coverage check skips `messages_fts%`, since the shadow tables are derived and repopulate on restore. `wrangler d1 export` does not work on databases with virtual tables; the app's own JSON backup is unaffected.

### Access control

Two independent auth surfaces:

- **Session cookie** (`ep_session`) — `getCurrentUser` / `requireUser` in `src/lib/auth/cookies.ts`, backed by `src/lib/auth/session.ts`. Used by dashboard/admin API routes. `requireUser` *throws*, which Next surfaces as a 500; routes use `requireSessionUser` from `src/lib/api/auth.ts`, which returns a proper 401 response (no route under `src/app` calls `requireUser` any more; keep it that way).
- **API key bearer token** — `authenticateApiKey` + `requireScope` in `src/lib/api/auth.ts`, used by the public `/api/v1/*` surface.

The session token lives only in the httpOnly cookie. Set it with `setSessionCookie` / `sessionCookieOptions(request)` (`src/lib/auth/session-cookie.ts`): `Secure` only in production *and* when the request is HTTPS (URL or `X-Forwarded-Proto`), so plain-http Docker can sign in. The web client keeps a non-secret marker in `localStorage` (`mailclaw-session`, `s1.<hex>`, `src/lib/auth/client-utils.ts`) that changes with the signed-in account, for cross-tab and cache keys. Clients from before this change kept the token itself (`mailclaw-session-token`); they move it once with `POST /api/auth/session` (Bearer only, sets the cookie), confirm with the cookie-only `GET /api/auth/session`, then drop it (`decideLegacyMigration`). Login, switch and logout put `token` in the JSON body only when `shouldReturnSessionToken(request)` (`login-response-utils.ts`): no `Sec-Fetch-Site` and no `Origin`, i.e. not a browser. Bearer session tokens still authenticate, for scripts such as `import-gmail-takeout.mjs`.

CSRF is enforced centrally: `rejectCrossSiteSessionMutation` (`src/lib/auth/origin.ts`) runs first in `worker.ts` `fetch` and in the Node server, and answers 403 `Cross-site request blocked` to any non-GET/HEAD/OPTIONS `/api/*` request that carries `ep_session` or `ep_accounts` and whose `Origin` is not the request's own origin. Bearer requests, cookie-less requests and `SESSION_ORIGIN_EXEMPT_PATHS` (`/api/inbound*`, `/api/public/`, `/api/i/`) pass. A new public endpoint that browsers on other origins post to with cookies must be added to that list. Routes keep their own `hasValidSessionMutationOrigin` checks as well.

The CSP (`src/lib/security/headers.ts`) adds `script-src-attr 'none'`: React binds events in script, so no inline handler attribute is needed, and an injected `<img onerror>` cannot run. Do not introduce `on*=` attributes in server-rendered HTML.

Mailbox content authorization goes through `src/lib/mailboxes/access.ts` (`getMailboxAccessLevel`, `listAccessibleMailboxes`, `listAccessibleMailboxIds`), which accounts for ownership and the `mailbox_access` sharing table. Message queries scope by accessible mailbox IDs, not by `userId` — see `src/app/api/messages/route.ts` for the canonical pattern. Mailbox details, aliases and avatars use `getMailboxSettingsAccess` in `src/lib/mailboxes/settings-access.ts`: the primary admin can configure any account's mailboxes, and admins with user-management permission can configure ordinary users' mailboxes. This does not grant access to their messages or sending identities. Primary mailbox names and avatars follow the mailbox owner's account identity.

### Folders are mostly virtual

`messages.status` is a free-text column driving the folder views: `received` (inbox), `sent`, `draft`, `spam`, `trash`, `archived`. Orthogonal to that are `starred`, `snoozedUntil`, and `folderId` (user-created folders in the `folders` table). A "folder" route under `src/app/(dashboard)/` is usually a status filter, not a table.

Counts come from `message_counters` (migration SQLite 0089, PostgreSQL/MySQL 0013): one row per (`mailbox_id`, `folder_key` (`''` outside a folder), `direction`, `status`, `read`, `starred`) with a `total`, kept by `message_counters_*` triggers on `messages` in all three dialects. Never write to it from application code. `loadMessageCounts` (`src/app/api/messages/counts/load.ts`) reads it in one `db.batch` with two small live queries (snoozed-now rows on `messages_mailbox_snoozed_idx`, scheduled sends), since those depend on the clock; JMAP `Mailbox/get` uses `loadCounterRows`. Readers left-join `folders` because MySQL fires no triggers for FK actions; for the same reason the daily cron runs `runMessageCounterRebuild` on MySQL only (after account purge). The table is in `INTERNAL_TABLES` (not backed up) and restore empties it before re-inserting messages. Users without mailboxes, and a database before 0089, fall back to the old grouped query (`loadGroupedMessageCounts`).

Lists page with `limit + 1`: `GET /api/messages` returns `hasMore` and a `total` that is a number only when the page proves it (`pageTotalWithoutCount`), else `null`; the client asks `?count=only` separately (cached per view, `src/hooks/message-total-cache.ts`). Pagination is still OFFSET, not keyset. Conversation pages read heads by primary key and thread members through the `(mailbox_id, thread_id)` index with an `EXISTS` recheck of the filter; see the comments in `route.ts` before "simplifying" those queries, because SQLite without statistics otherwise walks a folder's wide index.

Signed-in pages load through `GET /api/bootstrap` (session, mailboxes, assistant availability, DNS-skipped domains in one request; `src/lib/bootstrap/`), which `AuthGuard` starts from an inline script while the HTML parses. `/api/auth/me` and `/api/mailboxes` remain for refreshes and other callers and share the builders (`buildSessionInfo`, `listMailboxOptions`).

### Every feature ships unlocked

Every feature is available to every installation: branding, account management, shared mailboxes, account forwarding and booking hosts are unconditional. Authorization is ordinary admin/permission checking (`assertAdmin`, `canManageUsers`, `isPrimaryAdmin`, `getMailboxAccessLevel`); there is no plan, seat limit or activation step. The admin guards for account management live in `src/app/api/accounts/utils.ts` (`requireAccountsAdmin`) and `src/lib/api/admin-auth.ts` (API-key callers).

### Self-update

The admin overview dispatches `deploy-update.yml` (constant in `src/app/api/admin/update/utils.ts`) in the installation repo, which merges the upstream default branch and pushes it. It does not migrate, build, or deploy; the connected Cloudflare Git integration deploys the push. The admin update card separately reports and applies pending D1 migrations through the Worker binding.

## Conventions

- Tabs for indentation. `@/*` maps to `src/*`.
- Types and pure helpers are split out of components and modules into sibling `*-types.d.ts` and `*-utils.ts` files (41 and 27 of them respectively). Follow this when adding anything non-trivial.
- Server code reaches bindings through `getEnv()` / `getEnvAsync()` in `src/lib/cloudflare.ts`, then `getDb(env)` from `src/db` (cheap to call repeatedly on D1: the instance is cached per binding). Keep binding access centralized here.
- Request bodies that can be large or malformed are read with a size cap and parsed with zod, answering 400 for bad JSON or shape and 413 when too large (see `src/app/api/messages/bulk/` and `src/app/api/calendar/events/[eventId]/utils.ts`). Query-string integers go through `clampIntParam` (`src/lib/http/pagination.ts`).
- API routes return `NextResponse.json({ error: "..." }, { status })` for failures; there is no shared error envelope helper.
- UI is Tailwind v4 + shadcn/Radix primitives in `src/components/ui/`. `DialogContent` sets no max height, so a tall dialog overflows the viewport with an unreachable submit button — add `max-h-[calc(100vh-4rem)] overflow-y-auto` on any dialog with more than a few fields.
- `cloudflare-env.d.ts` is generated (500KB) — regenerate with `cf-typegen`, never hand-edit.
- App icons and the favicon are generated from `assets/icon.png`, never edited as PNGs: `node scripts/generate-icons.mjs write` rewrites `public/icon-48.png`, `icon-96.png`, `icon-192.png`, `icon-512.png` and `favicon.ico` (decode → Lanczos resample → plate composite → encode). `icon-192`/`icon-512` are square and fully opaque because launchers mask them and iOS paints transparent corners black; the smaller sizes keep the rounded plate for use inside the app.
